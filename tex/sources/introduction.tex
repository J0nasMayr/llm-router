\chapter{Introduction}
\label{chapter:introduction}

Every prompt submitted to a generative Large Language Model (LLM) triggers an inference job that consumes GPU time and energy.
It is important to realize that two prompts that look identical from the infrastructure's point of view may require vastly different capability:
a simple factual question, such as naming a country's capital, is answered correctly by a small model in well under a second, while a multi-step reasoning task may only be solved by a model more than an order of magnitude larger.
A provider that serves every prompt with its largest model therefore pays -- in energy and hardware time -- for capability most requests never use, while one that serves every prompt with a small model silently fails harder requests.
No single model dominates across the full space of prompt complexities \cite{greenserv, frugalgpt, routellm}, which has motivated a growing body of work on \emph{routing} each prompt to the cheapest model expected to answer it well \cite{cargo, tagrouter, noft, irtrouter, lookahead, greenserv}.
With generative AI already used by roughly 40\% of the U.S. working-age population \cite{Bick2024Rapid} and by nearly four-fifths of surveyed organizations \cite{McKinsey2025State}, the cost of these decisions accumulates over a very large number of requests.
One such router is GreenServ \cite{greenserv}, the system this thesis builds on.
GreenServ describes each prompt by its task type, its semantic cluster and its text complexity.
From these features, a contextual multi-armed bandit learns which model gives the best trade-off between answer accuracy and energy use.

Routing, however, is usually studied as if the chosen model were always available.
In practice, models run on a limited set of GPU nodes whose load changes from second to second, and inference increasingly spans the \emph{edge-cloud continuum}: small models on edge nodes close to the user, with little GPU memory and short queues, and large models on cloud nodes that are more capable but further away \cite{clone}.
In this setting, a routing decision can be right for the prompt and still wrong for the system.
Consider a router that has learned that hard math prompts are best answered by a large cloud model.
Such prompts come, for example, from GSM8K \cite{gsm8k}, a benchmark of grade-school math word problems that need several reasoning steps.
In GreenServ's measurements, a large cloud model such as Gemma 3 27B needs about 19\,s on average for such a problem.
If three such queries are already waiting on the cloud node, the next one is answered only after about 75\,s, while an idle edge model could have answered much sooner at a somewhat lower expected accuracy.
A router that cannot see the node's queue keeps choosing the large model, and every such query misses any reasonable deadline.
The queue is not the only hidden cost: a node holds only the models that fit into its GPU memory, and if a model is not among them, its weights must be loaded first.
This loading takes tens of seconds for the largest models.

This thesis addresses the following problem: \emph{given a pool of LLMs of different sizes, spread over edge and cloud nodes whose load changes at runtime, decide for each query which model answers and which node runs it, and decide which models each node keeps in GPU memory, such that the answers are accurate, arrive with low latency, and use the GPU time, memory and energy of the nodes efficiently.}
The three goals pull in different directions, so the thesis splits them between two decisions.
For each query, a router trades accuracy against energy, and it only considers models that are expected to answer within a latency deadline.
In the background, a controller decides which models stay loaded, so that the models the router wants can answer without waiting for a load, and the GPU memory holds the models that are in demand.

Existing work covers parts of this problem, but not all of it (Chapter~\ref{chapter:relatedWork}).
LLM serving systems \cite{bros, econoserve, dynamollm, nexussched} use the hardware efficiently, but treat every prompt as an opaque job and never choose a cheaper model for an easy one.
Prompt-aware routers choose a model per prompt but assume it is always available; GreenServ formulates a latency constraint but never enforces it.
Dynamic allocation systems \cite{enova, hasgpu, sageserve} adapt capacity to demand, but take the traffic per model as given rather than chosen by a router, and react mainly to aggregate demand.

To address this problem, this thesis extends GreenServ to the edge-cloud continuum.
A lightweight telemetry-driven feasibility filter first prunes nodes and models that are not expected to meet the latency deadline under the current hardware state, yielding a dynamic feasible set $M_t^*$.
The filter takes into account each node's queue, the models it holds in GPU memory, and the time it would need to load a missing model.
A contextual multi-armed bandit then selects a model from $M_t^*$ using GreenServ's prompt features and updates its policy online from an accuracy-energy reward.
Complementing these per-query decisions, a background \emph{allocation controller} decides which models each node keeps loaded and how each model's traffic is split across them.
It plans with the demand of the router: for every query, the model the bandit would choose if every model were loaded.
It adopts the Kalman-filter trigger design of HAS-GPU \cite{hasgpu} and plans with a small mixed-integer program, in the spirit of the replica and placement programs of ENOVA \cite{enova} and SageServe \cite{sageserve}.

The thesis answers three research questions:
\begin{description}
    \item[RQ1] Does excluding models whose nodes are not expected to meet the deadline, based on live per-node telemetry, reduce SLA violations compared to routing without hardware awareness?
    \item[RQ2] How much accuracy and energy efficiency does restricting the choice to feasible models cost, compared to GreenServ and to simple routing baselines?
    \item[RQ3] Does adapting which models each node keeps loaded to the router's demand reduce deadline violations and cold starts, compared to on-demand loading, an LRU cache and a fixed placement?
\end{description}

The contributions of this thesis are fourfold.
First, a formal problem model for edge-cloud LLM routing that treats latency feasibility as a constraint rather than an implicit reward penalty: whereas GreenServ formulates a latency constraint but does not enforce it in its experiments, this work estimates feasibility per (model, node) pair from live telemetry, including the time to load a model the node does not hold, and enforces it as a mask on the bandit's action set, while retaining GreenServ's accuracy-energy reward.
Second, an implementation of this architecture as a runtime pipeline of telemetry-driven feasibility filtering, semantic context extraction, and contextual bandit routing, deployed on an edge-cloud testbed with per-node task queues and inference workers that keep several models in GPU memory, follow a target placement, and report their queue, latencies, model load times and memory use.
Third, a demand-driven placement controller that decides which models each node keeps loaded and how each model's traffic is split across them. It combines HAS-GPU's Kalman-plus-threshold trigger -- extended with placement, latency-deviation and memory-pressure rules -- with a small mixed-integer program, and plans with the router's shadow demand, so that the models the bandit wants are loaded even while the feasibility filter masks them.
Fourth, an empirical evaluation on this testbed that answers RQ1 (Section~\ref{sec:eval-filter}), RQ2 (Section~\ref{sec:eval-routing}), and RQ3 (Section~\ref{sec:eval-allocation}).
