\chapter{System Model}
\label{chapter:model}

The objective of this work is to dynamically orchestrate Large Language Model (LLM) inference tasks across an Edge-Cloud continuum. The system aims to maximize inference accuracy while minimizing physical energy consumption. Furthermore, real-time latency constraints dictated by the hardware's current operational state are considered.

\section{Problem Formulation}
\label{sec:problem}

Consider a distributed computing environment consisting of a set of nodes $N$, comprising both resource-constrained edge nodes and high-capacity cloud nodes; $\mathrm{tier}(n)$ denotes whether node $n \in N$ belongs to the edge or the cloud tier. Let $M = \{m_1, m_2, \dots, m_K\}$ denote the heterogeneous pool of LLMs. Each model is assigned to one tier: a subset of smaller models $M_{edge} \subset M$ is only executed on edge nodes, while larger, high-precision models $M_{cloud} \subset M$ are only executed on cloud nodes. Nodes do not host a fixed set of models: a node loads the model a task requests on demand and keeps as many models in GPU memory as fit into its memory budget $S_n$, which is its GPU memory minus a headroom $H$ for activations and the KV cache. When a new model does not fit, the node unloads the models it has used least recently until the new one fits.

The system processes a stream of user queries over time. At each discrete time step $t$, a user submits a query $q_t$. Upon arrival, the system must select exactly one model $m_t \in M$ to execute the inference, and one node of the model's tier to run it.

To ensure Quality of Service (QoS), the system should satisfy a latency deadline $T_{max}$. The latency of executing a query with model $m$ on node $n$ is estimated as
$$ \hat{T}(m, n) = \delta_{\mathrm{tier}(n)} + L(m, n) + (W_n + 1) \cdot \bar{\tau}(m, n), $$
the sum of a tier-dependent network delay $\delta$, the time $L(m, n)$ the query waits for a model load, and a queue-aware processing estimate: $W_n$ is the number of tasks waiting in node $n$'s queue and $\bar{\tau}(m, n)$ is the node's recent average inference latency for $m$, so a node that is currently overloaded - or that has historically been slow for $m$ - yields a correspondingly larger estimate. The load term is needed because a node holds only the models that fit into its memory budget: a task for any other model must wait until that model's weights are loaded into GPU memory. Let $\ell(m, n)$ be the time node $n$ needs to load $m$. It is the average of the node's last five loads of $m$. Before the first load, it is estimated as the size of $m$'s weights (2\,GB per billion parameters in bf16) divided by an assumed load speed $B$. With $B = 2$\,GB/s, this ranges from about 0.5\,s for the smallest to about 34\,s for the largest model of the pool, so a single load can exceed the deadline on its own. If $n$ holds $m$, then $L(m, n) = 0$; if not, $L(m, n) = \ell(m, n)$. If $n$ is loading a model $m'$ at that moment, the rest of this load is added, estimated as $\ell(m', n)$ minus the time the load has already run. If $m' = m$, only this rest counts. Tasks that already wait in the queue are assumed to need no further model load. The estimate can therefore be too optimistic when queued tasks need models the node does not hold, because loading them may also unload $m$. The estimate depends only on the model and the node's state, not on the query itself; prompt and output lengths are not taken into account. Before latencies are estimated, nodes whose free GPU memory $G_n$ falls below a threshold $G_{min}$ are pruned, leaving the surviving nodes $N_t$. This threshold is a coarse safety net against nodes close to running out of memory. In addition, a model is only considered on nodes whose memory budget can hold it, i.e.\ where $s_m \le S_n$. Here $s_m$ is the memory model $m$ took when the node last loaded it; before the first load, it is estimated as 2\,GB per billion parameters. A model is feasible if at least one surviving node of its tier can hold it and is expected to meet the deadline, which establishes a dynamic set of feasible models:
$$ M_t^* = \{m \in M \mid \exists\, n \in N_t : \mathrm{tier}(n) = \mathrm{tier}(m) \,\wedge\, s_m \le S_n \,\wedge\, \hat{T}(m, n) \le T_{max}\} $$
For the selected model $m_t \in M_t^*$, the system observes an inference accuracy $Acc(m_t, q_t)$ and an energy cost $E(m_t, q_t)$. The routing problem is formulated as a multi-objective optimization task maximizing the scalarized reward $r_t$:
$$ r_t = \alpha \cdot Acc(m_t, q_t) - \beta \cdot E(m_t, q_t) $$
where $\alpha$ and $\beta$ are weighting parameters that specify the trade-off between output quality and energy efficiency. $Acc$ is the quality metric of the query's task. For the multiple-choice tasks and GSM8K, it is exact match after extracting the answer letter or the final numeric answer; for summarization, it is a simplified ROUGE-1 recall \cite{rouge}, the fraction of distinct words of the reference summary that also appear in the generated one. Following GreenServ, $E$ is the GPU energy consumed per processed (input and output) token. Both terms are normalized to $[0, 1]$ per task type before being combined, so the bandit always compares arms on the same scale regardless of the absolute units of accuracy and energy. The normalization uses fixed minimum and maximum values obtained from GreenServ's offline profiling of the same model pool; values outside these bounds are clamped, and a query without a known task type receives the neutral value $0.5$ for both terms. The implementation computes the energy term in its efficiency form, $r_t = \alpha \cdot Acc + \beta \cdot (1 - E)$, which differs from the formulation above only by the additive constant $\beta$ and therefore induces the same preference ordering over models. With $\alpha = 1 - \lambda$ and $\beta = \lambda$, this is exactly GreenServ's single-parameter reward with trade-off weight $\lambda$; this work uses $\alpha = \beta = 0.5$, i.e.\ GreenServ's default $\lambda = 0.5$. Computing $Acc$ requires a reference answer, which the benchmark workloads used in this thesis provide; queries without a reference are routed normally but do not update the routing policy. Because the true accuracy and energy consumption are only observed for the selected model after execution, the system must continuously learn the optimal routing policy online.


\section{Proposed Method}
\label{sec:method}

To solve the routing problem defined above, this thesis proposes a four-stage scheduling pipeline, complemented by a background allocation control loop (Section~\ref{sec:allocation}) that adapts how each model's traffic is distributed across nodes. Figure~\ref{fig:architecture} gives an overview. The architecture bridges real-time hardware telemetry with semantic prompt analysis to achieve resource-aware and prompt-aware inference.

\noindent
The proposed architecture operates through the following sequential stages:

\textbf{1. Telemetry and Feasibility Filtering:}
Every edge and cloud node runs an inference worker that, in a background thread, publishes its current state to a shared store every few seconds: the length of its task queue $W_n$, its free GPU memory $G_n$, and its rolling average inference latency $\bar{\tau}(m, n)$ for every model it has executed. It also reports the models it holds in GPU memory, a model load in progress with the time it has been running, the average load time $\ell(m, n)$ and the memory $s_m$ of every model it has loaded, and its memory budget $S_n$. Each entry expires shortly after its last update, so nodes that stop reporting drop out automatically. To minimize unnecessary network transmission delays, the central scheduler is deployed as a gateway at the Edge tier. This allows it to be the initial point of contact and intercept incoming queries. When query $q_t$ arrives, the scheduler reads the latest state of all nodes, prunes any node whose free GPU memory falls below $G_{min}$, and evaluates $\hat{T}(m, n)$ for every model on the surviving nodes of its tier that can hold it. Any model for which no such node meets $T_{max}$ is excluded, yielding the feasible set $M_t^*$. Once the allocation controller (Section~\ref{sec:allocation}) has produced its eligibility map, only the nodes the map lists for a model are considered for it, so the map shapes $M_t^*$ as well as the dispatch decision of Stage~3. If node $n$ has not yet executed $m$, $\bar{\tau}(m, n)$ falls back to the node's average over the models it has served; a node that has served nothing yet reports zero, so only the network delay and the load time of the model count for it. This way, new nodes and untried models can still receive traffic. The filter is a best-effort mechanism built on estimates, not a hard guarantee: when no telemetry is available (e.g.\ at start-up) or no model is feasible, the scheduler does not reject the query. The bandit then chooses among all models, and the query is placed on a shared fallback queue of the chosen model's tier, which every node of that tier consumes after its own queue.

\textbf{2. Semantic Context Extraction:}
Next, the incoming query $q_t$ is passed through a lightweight context generator. This module extracts key semantic features from the prompt to evaluate its complexity without performing full inference. Following the methodology established by GreenServ, the module extracts three specific features: Task Type, Semantic Cluster (via online $k$-means with $k = 3$ over sentence embeddings), and Text Complexity (via the Flesch Reading Ease formula, inverted so that higher values denote harder text and binned into the intervals $[0, 33)$, $[33, 67)$ and $[67, 100]$). As in GreenServ's own experiments, the task type is the label of the benchmark dataset a query is drawn from, which the client submits together with the query; a query without such a label receives an all-zero task-type component. GreenServ additionally describes a lightweight classifier for unlabeled queries, which is not used in this work. Each feature is one-hot encoded, and the three encodings are concatenated into the context vector $x_t \in \{0, 1\}^d$ with $d = 5 + 3 + 3 = 11$ (five task types, three clusters, three complexity bins).

\textbf{3. Contextual Bandit Routing:}
With the feasible hardware set $M_t^*$ and the semantic context vector $x_t$ established, the system employs a Contextual Multi-Armed Bandit (MAB) algorithm to make the final routing decision. Specifically, the Linear Upper Confidence Bound (LinUCB) algorithm is utilized. The algorithm assumes a linear relationship between the context $x_t$ and the expected reward of each model arm. LinUCB calculates the expected reward for all $m \in M_t^*$, balancing the use of historically successful models for similar prompts with the exploration of uncertain models; models outside $M_t^*$ are masked by forcing their score to $-\infty$, so the bandit can only choose physically viable arms. The model $m_t$ that yields the highest upper confidence bound is selected.
The bandit decides \emph{which model} answers; a final dispatch step decides \emph{which node} executes it. Among the surviving nodes of $m_t$'s tier that meet $T_{max}$, the scheduler selects the node with the lowest estimate $\hat{T}(m_t, n)$ -- or, when the allocation controller of Section~\ref{sec:allocation} has produced traffic weights for $m_t$, draws one of these nodes at random in proportion to those weights. Since $\hat{T}$ includes the load time, a node that would first have to load $m_t$ can fail the deadline check, and the lowest estimate favours nodes that already hold $m_t$. The query is then enqueued to that node's dedicated task queue.

\textbf{4. Execution and Policy Update (Feedback Loop):}
The selected node executes the inference task: its worker loads $m_t$ if it is not already in GPU memory, after unloading its least recently used models if $m_t$ does not fit next to them. The worker then generates the response with the generation settings of the query's task (e.g.\ a single output token for multiple-choice tasks), and measures the GPU energy of the generation step. Loading a model is not part of these measurements. Its duration is measured separately: it includes unloading models to make room and a short warm-up run, is reported with the result, and updates the node's load time $\ell(m_t, n)$. The worker also records the memory $s_{m_t}$ the model takes. The energy spent on loading is not measured. The scheduler polls for the result and returns the response to the user. If a reference answer is available, the scheduler computes $Acc(m_t, q_t)$ and $E(m_t, q_t)$ as defined in Section~\ref{sec:problem} and the final reward $r_t$. This scalar reward is fed back into the LinUCB agent, which updates its parameter matrices. Since several queries can be in flight at once, this feedback arrives with a delay, possibly after later queries have already been routed. This continuous feedback loop lets the scheduler adapt to distribution shifts in user queries and, through the feasibility mask, to models that are temporarily unavailable within the computing continuum; the set of arms itself is fixed when the system starts.

\section{Dynamic Per-Model Traffic Allocation}
\label{sec:allocation}

The pipeline above decides, per query, which model answers and which node executes it -- but it takes as given which nodes may serve a model and how the model's traffic should be spread across them. A background \emph{allocation controller} closes this remaining loop: it consumes the same telemetry as Stage~1, evaluates a set of trigger rules at a fixed interval, and, whenever a rule fires, recomputes for every model the set of nodes it may use and the proportion in which its traffic is split across them. The controller only reshapes traffic: it does not load, unload or pin models on nodes. Each node loads requested models on demand and unloads the models it has used least recently when a new one does not fit. The design adopts the lightweight trigger of HAS-GPU \cite{hasgpu} -- classical state-space estimation paired with simple threshold rules -- and an allocation program in the spirit of ENOVA \cite{enova}, while deliberately avoiding heavier machinery such as learned anomaly detectors.

\subsection{Load Prediction and Trigger}

For each model $m$, the controller maintains a scalar Kalman filter over its observed request rate $R_t^{(m)}$ -- the number of queries routed to $m$ since the previous evaluation, divided by the elapsed time, which is zero if $m$ received none -- yielding the prediction
$$ \hat{R}_t^{(m)} = \hat{R}_{t-1}^{(m)} + K_t \big( R_t^{(m)} - \hat{R}_{t-1}^{(m)} \big), \qquad K_t = \frac{P_{t-1} + Q}{P_{t-1} + Q + D}, $$
where the process noise $Q$ and observation noise $D$ are the only hyperparameters; the gain $K_t$ self-adjusts between them, reducing the filter to a self-tuning exponential smoother. The prediction is compared against the model's current serving capacity
$$ C^{(m)} = \sum_{n} \frac{w_{m,n}}{\bar{\tau}(m, n)}, $$
the weighted sum of the inverse average latencies over the model's currently eligible nodes.

A re-allocation is triggered when any of the following rules fires, all gated by a single cooldown interval $T_{cool}$ to suppress oscillation; the very first allocation is computed as soon as telemetry becomes available:
\begin{itemize}
    \item \textbf{Scale-up:} $\hat{R}^{(m)} > \theta_{up} \cdot C^{(m)}$ for any model $m$ -- predicted demand approaches capacity.
    \item \textbf{Scale-down:} $\hat{R}^{(m)} < \theta_{down} \cdot C^{(m)}$ for all models with non-zero capacity, provided at least one predicted rate exceeds a keep-alive floor $R_{min}$ -- capacity is broadly over-provisioned.
    \item \textbf{Latency deviation:} the average latency of a (model, node) pair most recently reported by the node -- a rolling mean over its last executions of the model -- exceeds the pair's own Kalman prediction by more than $\kappa$ standard deviations of its recent residuals -- the pair is misbehaving relative to its history. The rule becomes active after a few observations, and the standard deviation is floored at a fraction of the prediction so that a perfectly stable history does not make the threshold unreachable.
    \item \textbf{Memory pressure:} a node's free GPU memory $G_n$ falls below $G_{min}$ -- the node can no longer safely host additional work.
\end{itemize}
The first two rules follow HAS-GPU, whose request-rate-only trigger suffices for homogeneous serverless functions. For heterogeneous LLM routing they are insufficient on their own: per-request cost varies by orders of magnitude with prompt length, the bandit shifts load between small edge models and large cloud models at constant arrival rate, and long-context requests can exhaust GPU memory at low request rates. The latency-deviation and memory-pressure rules extend the trigger to cover exactly these cases. The thresholds $\theta_{up}$ and $\theta_{down}$ are deliberately far apart ($\theta_{up} = 0.85$, $\theta_{down} = 0.5$): this hysteresis band prevents the controller from alternating between scale-up and scale-down decisions when demand hovers around a single threshold. Since one cooldown gates every rule, the controller reacts to rising and falling load at the same pace, at most once per $T_{cool}$.

\subsection{Allocation Program}

When the trigger fires, the controller re-solves a small linear program over the traffic-split variables $x_{m,n} \in [0, 1]$, the fraction of model $m$'s traffic routed to node $n$:
$$ \begin{aligned} \min_{x} \;\; & \sum_{m, n} d_m \, \bar{\tau}(m, n) \, x_{m,n} \\ \text{s.t.} \;\; & \sum_{n} x_{m,n} = 1 \quad \forall m \in M^{elig}, \qquad \sum_{m} d_m \, \bar{\tau}(m, n) \, x_{m,n} \le 1 \quad \forall n, \end{aligned} $$
with $x_{m,n} = 0$ fixed for ineligible pairs (tier mismatch, a model that does not fit into the node's memory budget, or memory pressure), and $M^{elig} \subseteq M$ the models with at least one eligible node. Models outside $M^{elig}$ are left out of the program -- their equality constraint could never hold and would render the whole program infeasible -- and receive an empty eligibility entry, so the routing stage masks them. Here $d_m = \max(\hat{R}^{(m)}, d_{min})$ is the predicted demand, floored at a small $d_{min}$ so that models without recent traffic keep a minimal share of capacity, and $\bar{\tau}(m, n)$ is the pair's average latency, with the same fallback as in Stage~1 and a nominal $\bar{\tau}_0$ for nodes without any history. The objective thus minimizes total node-busy time while the per-node constraint prevents any node from being saturated beyond its throughput. The solution yields the per-model eligibility map $m \mapsto \{(n, w_{m,n})\}$ with $w_{m,n} = x_{m,n}$, which Stage~1 and the dispatch step of Stage~3 consult. If the program is infeasible under the current demand, the controller falls back to equal weights over each model's eligible nodes, preserving availability over optimality.
