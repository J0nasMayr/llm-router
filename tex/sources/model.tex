\chapter{System Model}
\label{chapter:model}

The objective of this work is to dynamically orchestrate Large Language Model (LLM) inference tasks across an Edge-Cloud continuum.
The system pursues three goals: high accuracy, low latency, and an efficient use of the nodes' resources -- GPU time, memory and energy.
Two decisions share these goals.
For each query, a router selects the model and the node: it trades accuracy against energy, and it only considers models that are expected to meet a latency deadline under the current state of the hardware (Sections~\ref{sec:problem} and~\ref{sec:method}).
In the background, an allocation controller decides which models the nodes keep loaded: it keeps the models the router asks for in memory, so that queries rarely wait for a model load and the nodes spend their GPU time and memory on the models in demand (Section~\ref{sec:allocation}).

\section{Problem Formulation}
\label{sec:problem}

Consider a distributed computing environment consisting of a set of nodes $N$, comprising both resource-constrained edge nodes and high-capacity cloud nodes;
$\mathrm{tier}(n)$ denotes whether node $n \in N$ belongs to the edge or the cloud tier.
Let $M = \{m_1, m_2, \dots, m_K\}$ denote the heterogeneous pool of LLMs.
Each model is assigned to one tier: a subset of smaller models $M_{edge} \subset M$ is only executed on edge nodes, while larger, high-precision models $M_{cloud} \subset M$ are only executed on cloud nodes.
Nodes do not host a fixed set of models.
A node keeps as many models in GPU memory as fit into its memory budget $S_n$, which is its GPU memory minus a headroom $H$ for activations and the KV cache.
It loads the models that an allocation controller assigns to it (Section~\ref{sec:allocation}), and any other model a task requests on demand.
When a new model does not fit, the node unloads the models it has used least recently until the new one fits, starting with those the controller has not assigned to it.

The system processes a stream of user queries over time.
At each discrete time step $t$, a user submits a query $q_t$.
Upon arrival, the system must select exactly one model $m_t \in M$ to execute the inference, and one node of the model's tier to run it.
In the background, the system also decides which models each node keeps loaded.
That decision serves the latency and resource goals and is formulated in Section~\ref{sec:allocation}.

To ensure Quality of Service (QoS), the system should satisfy a latency deadline $T_{max}$.
The latency of executing a query with model $m$ on node $n$ is estimated as
$$ \hat{T}(m, n) = \delta_{\mathrm{tier}(n)} + L(m, n) + (W_n + 1) \cdot \bar{\tau}(m, n), $$
the sum of a tier-dependent network delay $\delta$, the time $L(m, n)$ the query waits for a model load, and a queue-aware processing estimate:
$W_n$ is the number of tasks waiting in node $n$'s queue and $\bar{\tau}(m, n)$ is the node's recent average inference latency for $m$, so a node that is currently overloaded - or that has historically been slow for $m$ - yields a correspondingly larger estimate.
The load term is needed because a node holds only the models that fit into its memory budget: a task for any other model must wait until that model's weights are loaded into GPU memory.
Let $\ell(m, n)$ be the time node $n$ needs to load $m$. It is the average of the node's last five loads of $m$. Before the first load, it is estimated as the size of $m$'s weights (2\,GB per billion parameters in bf16) divided by an assumed load speed $B$.
With $B = 2$\,GB/s, this ranges from about 0.5\,s for the smallest to about 34\,s for the largest model of the pool, so a single load can exceed the deadline on its own.
If $n$ holds $m$, then $L(m, n) = 0$; if not, $L(m, n) = \ell(m, n)$. If $n$ is loading a model $m'$ at that moment, the rest of this load is added, estimated as $\ell(m', n)$ minus the time the load has already run. If $m' = m$, only this rest counts.
Tasks that already wait in the queue are assumed to need no further model load. The estimate can therefore be too optimistic when queued tasks need models the node does not hold, because loading them may also unload $m$.
The estimate depends only on the model and the node's state, not on the query itself; prompt and output lengths are not taken into account. Before latencies are estimated, nodes whose free GPU memory $G_n$ falls below a threshold $G_{min}$ are pruned, leaving the surviving nodes $N_t$.
This threshold is a coarse safety net against nodes close to running out of memory. In addition, a model is only considered on nodes whose memory budget can hold it, i.e.\ where $s_m \le S_n$.
Here $s_m$ is the memory model $m$ took when the node last loaded it; before the first load, it is estimated as 2\,GB per billion parameters.
A model is feasible if at least one surviving node of its tier can hold it and is expected to meet the deadline, which establishes a dynamic set of feasible models:
$$ M_t^* = \{m \in M \mid \exists\, n \in N_t : \mathrm{tier}(n) = \mathrm{tier}(m) \,\wedge\, s_m \le S_n \,\wedge\, \hat{T}(m, n) \le T_{max}\} $$
For the selected model $m_t \in M_t^*$, the system observes an inference accuracy $Acc(m_t, q_t)$ and an energy cost $E(m_t, q_t)$.
The routing problem is formulated as a multi-objective optimization task maximizing the scalarized reward $r_t$:
$$ r_t = \alpha \cdot Acc(m_t, q_t) - \beta \cdot E(m_t, q_t) $$
where $\alpha$ and $\beta$ are weighting parameters that specify the trade-off between output quality and energy efficiency.
$Acc$ is the quality metric of the query's task.
For the multiple-choice tasks and GSM8K, it is exact match after extracting the answer letter or the final numeric answer; for summarization, it is a simplified ROUGE-1 recall \cite{rouge}, the fraction of distinct words of the reference summary that also appear in the generated one.
Following GreenServ, $E$ is the GPU energy consumed per processed (input and output) token. Both terms are normalized to $[0, 1]$ per task type before being combined, so the bandit always compares arms on the same scale regardless of the units of accuracy and energy.
The normalization uses fixed minimum and maximum values obtained from GreenServ's offline profiling of the same model pool; values outside these bounds are clamped, and a query without a known task type receives the neutral value $0.5$ for both terms.
The implementation computes the energy term in its efficiency form, $r_t = \alpha \cdot Acc + \beta \cdot (1 - E)$, which differs from the formulation above only by the additive constant $\beta$ and therefore induces the same preference ordering over models.
With $\alpha = 1 - \lambda$ and $\beta = \lambda$, this is exactly GreenServ's single-parameter reward with trade-off weight $\lambda$; this work uses $\alpha = \beta = 0.5$, i.e.\ GreenServ's default $\lambda = 0.5$.
Computing $Acc$ requires a reference answer, which the benchmark workloads used in this thesis provide; queries without a reference are routed normally but do not update the routing policy.
Because the true accuracy and energy consumption are only observed for the selected model after execution, the system must continuously learn the optimal routing policy online.


\section{Proposed Method}
\label{sec:method}

To solve the routing problem defined above, this thesis proposes a four-stage scheduling pipeline, complemented by a background allocation controller (Section~\ref{sec:allocation}) that decides which models each node keeps loaded and how each model's traffic is split across them.
Figure~\ref{fig:architecture} gives an overview.
The architecture bridges real-time hardware telemetry with semantic prompt analysis to achieve resource-aware and prompt-aware inference.

\noindent
The proposed architecture operates through the following sequential stages:

\textbf{1. Telemetry and Feasibility Filtering:}
Every edge and cloud node runs an inference worker that, in a background thread, publishes its current state to a shared store every few seconds: the length of its task queue $W_n$, its free GPU memory $G_n$, and its rolling average inference latency $\bar{\tau}(m, n)$ for every model it has executed.
It also reports the models it holds in GPU memory, a model load in progress with the time it has been running, the average load time $\ell(m, n)$ and the memory $s_m$ of every model it has loaded, and its memory budget $S_n$.
Each entry expires shortly after its last update, so nodes that stop reporting drop out automatically.
To minimize unnecessary network transmission delays, the central scheduler is deployed as a gateway at the Edge tier. This allows it to be the initial point of contact and intercept incoming queries.
When query $q_t$ arrives, the scheduler reads the latest state of all nodes, prunes any node whose free GPU memory falls below $G_{min}$, and evaluates $\hat{T}(m, n)$ for every model on the surviving nodes of its tier that can hold it.
Any model for which no such node meets $T_{max}$ is excluded, yielding the feasible set $M_t^*$.
Once the allocation controller (Section~\ref{sec:allocation}) has made a plan, a model that has replicas in it is considered only on the nodes that hold it.
If none of them meets $T_{max}$, the other nodes of its tier serve as overflow and load the model on demand.
Models without replica are not restricted. If node $n$ has not yet executed $m$, $\bar{\tau}(m, n)$ falls back to the node's average over the models it has served; a node that has served nothing yet reports zero, so only the network delay and the load time of the model count for it.
This way, new nodes and untried models can still receive traffic. The filter is a best-effort mechanism built on estimates, not a hard guarantee: when no telemetry is available (e.g.\ at start-up) or no model is feasible, the scheduler does not reject the query.
The bandit then chooses among all models, and the query is placed on a shared fallback queue of the chosen model's tier, which every node of that tier consumes after its own queue.

\textbf{2. Semantic Context Extraction:}
Next, the incoming query $q_t$ is passed through a lightweight context generator.
This module extracts key semantic features from the prompt to evaluate its complexity without performing full inference.
Following the methodology established by GreenServ, the module extracts three specific features: Task Type, Semantic Cluster (via online $k$-means with $k = 3$ over sentence embeddings), and Text Complexity (via the Flesch Reading Ease formula, inverted so that higher values denote harder text and binned into the intervals $[0, 33)$, $[33, 67)$ and $[67, 100]$).
As in GreenServ's own experiments, the task type is the label of the benchmark dataset a query is drawn from, which the client submits together with the query; a query without such a label receives an all-zero task-type component.
GreenServ additionally describes a lightweight classifier for unlabeled queries, which is not used in this work.
Each feature is one-hot encoded, and the three encodings are concatenated into the context vector $x_t \in \{0, 1\}^d$ with $d = 5 + 3 + 3 = 11$ (five task types, three clusters, three complexity bins).

\textbf{3. Contextual Bandit Routing:}
With the feasible hardware set $M_t^*$ and the semantic context vector $x_t$ established, the system employs a Contextual Multi-Armed Bandit (MAB) algorithm to make the final routing decision.
Specifically, the Linear Upper Confidence Bound (LinUCB) algorithm is utilized. The algorithm assumes a linear relationship between the context $x_t$ and the expected reward of each model arm.
LinUCB calculates the expected reward for all $m \in M_t^*$, balancing the use of historically successful models for similar prompts with the exploration of uncertain models; models outside $M_t^*$ are masked by forcing their score to $-\infty$, so the bandit can only choose physically viable arms.
The model $m_t$ that yields the highest upper confidence bound is selected. The bandit also records its \emph{shadow choice}: the model with the highest score before masking, i.e.\ the model it would choose if every model were loaded. The allocation controller plans with these choices (Section~\ref{sec:allocation}).
The bandit decides \emph{which model} answers; a final dispatch step decides \emph{which node} executes it.
Among the surviving nodes of $m_t$'s tier that meet $T_{max}$, the scheduler selects the node with the lowest estimate $\hat{T}(m_t, n)$ -- or, when the controller's plan has replicas of $m_t$, draws one of the replicas at random in proportion to its traffic shares $w_{m_t,n}$.
Since $\hat{T}$ includes the load time, a node that would first have to load $m_t$ can fail the deadline check, and the lowest estimate favours nodes that already hold $m_t$.
The query is then enqueued to that node's dedicated task queue.

\textbf{4. Execution and Policy Update (Feedback Loop):}
The selected node executes the inference task: its worker loads $m_t$ if it is not already in GPU memory, after unloading its least recently used models if $m_t$ does not fit next to them -- first those outside the node's target placement (Section~\ref{sec:allocation}).
The worker then generates the response with the generation settings of the query's task (e.g.\ a single output token for multiple-choice tasks), and measures the GPU energy of the generation step.
Loading a model is not part of these measurements.
Its duration is measured separately: it includes unloading models to make room and a short warm-up run, is reported with the result, and updates the node's load time $\ell(m_t, n)$.
The worker also records the memory $s_{m_t}$ the model takes.
The scheduler polls for the result and returns the response to the user.
If a reference answer is available, the scheduler computes $Acc(m_t, q_t)$ and $E(m_t, q_t)$ as defined in Section~\ref{sec:problem} and the final reward $r_t$.
This scalar reward is fed back into the LinUCB agent, which updates its parameter matrices.
Since several queries can be in flight at once, this feedback arrives with a delay, possibly after later queries have already been routed.
This continuous feedback loop lets the scheduler adapt to distribution shifts in user queries and, through the feasibility mask, to models that are temporarily unavailable within the computing continuum; the set of arms itself is fixed when the system starts.

\section{Demand-Driven Model Placement}
\label{sec:allocation}

The pipeline above decides, per query, which model answers and which node runs it.
It takes as given which models the nodes hold in GPU memory.
A background \emph{allocation controller} closes this loop.
It decides which models each node keeps loaded -- the \emph{placement} -- and how each model's traffic is split across the nodes that hold it.
The controller consumes the same telemetry as Stage~1, evaluates a set of trigger rules at a fixed interval, and makes a new plan whenever a rule fires.
It writes the \emph{target placement} of each node, the list of models the node should keep loaded, to the shared store, and the nodes follow it.
The design adopts the lightweight trigger of HAS-GPU \cite{hasgpu} -- classical state-space estimation paired with simple threshold rules -- and a placement program in the spirit of the replica program of ENOVA \cite{enova} and the placement program of SageServe \cite{sageserve}.
Unlike these systems, the controller plans with the demand of the router.
The controller is optional: without it, each node keeps the models it has used most recently, i.e.\ it works as a least-recently-used (LRU) cache of models.

\subsection{Shadow Demand and Trigger}

The controller plans with the \emph{shadow demand}: for every query, the model the bandit would choose if every model were loaded (its shadow choice, Stage~3).
Planning with the realized demand -- the models the queries are actually routed to -- would lock models out.
A model that no node holds is often masked, so the bandit cannot choose it, its demand stays at zero, and it is never loaded.
The shadow demand also contains the exploration of the bandit, so a model the bandit wants to try can be loaded if the placement program finds it worthwhile.

For each model $m$, the controller maintains a scalar Kalman filter over its shadow request rate $R_t^{(m)}$ -- the number of queries whose shadow choice was $m$ since the previous evaluation, divided by the elapsed time, which is zero if there were none -- yielding the prediction
$$ \hat{R}_t^{(m)} = \hat{R}_{t-1}^{(m)} + K_t \big( R_t^{(m)} - \hat{R}_{t-1}^{(m)} \big), \qquad K_t = \frac{P_{t-1} + Q}{P_{t-1} + Q + D}, $$
where the process noise $Q$ and observation noise $D$ are the only hyperparameters; the gain $K_t$ self-adjusts between them, reducing the filter to a self-tuning exponential smoother.
The prediction is compared against the capacity of the model's replicas
$$ C^{(m)} = \sum_{n} \frac{w_{m,n}}{\bar{\tau}(m, n)}, $$
the weighted sum of the inverse average latencies over the nodes that hold $m$ in the current plan, with $w_{m,n}$ the traffic shares defined below.

A new plan is triggered when any of the following rules fires, all gated by a single cooldown interval $T_{cool}$ to suppress oscillation:
\begin{itemize}
    \item \textbf{Scale-up:} $\hat{R}^{(m)} > \theta_{up} \cdot C^{(m)}$ for a model $m$ with replicas -- predicted demand approaches the capacity of its replicas.
    \item \textbf{Placement:} $\hat{R}^{(m)} > 1 / T_{plan}$ for a model $m$ without replica -- the router asks for a model that no node holds, often enough that loading it can pay off.
    \item \textbf{Scale-down:} $\hat{R}^{(m)} < \theta_{down} \cdot C^{(m)}$ for all models with replicas, provided at least one predicted rate exceeds a keep-alive floor $R_{min}$ -- capacity is broadly over-provisioned.
    \item \textbf{Latency deviation:} the average latency of a (model, node) pair most recently reported by the node -- a rolling mean over its last executions of the model -- exceeds the pair's own Kalman prediction by more than $\kappa$ standard deviations of its recent residuals -- the pair is misbehaving relative to its history. The rule becomes active after a few observations, and the standard deviation is floored at a fraction of the prediction so that a perfectly stable history does not make the threshold unreachable.
    \item \textbf{Memory pressure:} a node's free GPU memory $G_n$ falls below $G_{min}$ -- the node can no longer safely host additional work.
\end{itemize}
The scale-up and scale-down rules follow HAS-GPU, whose request-rate-only trigger suffices for homogeneous serverless functions.
For heterogeneous LLM routing they are insufficient on their own: per-request cost varies by orders of magnitude with prompt length, the bandit shifts load between small edge models and large cloud models at constant arrival rate, and long-context requests can exhaust GPU memory at low request rates.
The latency-deviation and memory-pressure rules extend the trigger to cover exactly these cases.
The placement rule is needed because a model may have no replica at all, while HAS-GPU always keeps at least one instance of each function.
Its threshold is the break-even of the placement program below, about one request per planning horizon $T_{plan}$, so the rule fires whenever the program might decide to load the model.
The thresholds $\theta_{up}$ and $\theta_{down}$ are deliberately far apart ($\theta_{up} = 0.85$, $\theta_{down} = 0.5$): this prevents the controller from alternating between scale-up and scale-down decisions when demand hovers around a single threshold.
Since one cooldown gates every rule, the controller reacts to rising and falling load at the same pace, at most once per $T_{cool}$.

The first plan is made as soon as telemetry is available.
Its demand is a prior: the share of GreenServ's 2,500 profiled queries for which each model gives the highest reward at $\lambda = 0.5$, scaled to an assumed total request rate.
A fixed placement, used as a baseline in Chapter~\ref{chapter:evaluation}, keeps this first plan.

\subsection{Placement Program}

When the trigger fires, the controller solves a small mixed-integer program.
For each eligible (model, node) pair, $y_{m,n} \in \{0, 1\}$ states whether node $n$ keeps model $m$ loaded, and $f_{m,n} \in [0, 1]$ is the share of $m$'s requests that $n$ serves:
$$ \begin{aligned} \min_{y, f} \;\; & \sum_{m, n} \hat{R}^{(m)} \, \bar{\tau}(m, n) \, f_{m,n} + \sum_{m} \hat{R}^{(m)} \, (\bar{\tau}_m + \bar{\ell}_m) \Big( 1 - \sum_{n} f_{m,n} \Big) \\ & + \sum_{m, n} \frac{\ell(m, n)}{T_{plan}} \, y_{m,n} \, (1 - y^0_{m,n}) \\ \text{s.t.} \;\; & \sum_{n} f_{m,n} \le 1 \quad \forall m, \qquad f_{m,n} \le y_{m,n} \quad \forall m, n, \\ & \sum_{m} s_m \, y_{m,n} \le S_n \quad \forall n, \qquad \sum_{m} \hat{R}^{(m)} \, \bar{\tau}(m, n) \, f_{m,n} \le \theta_{up} \quad \forall n. \end{aligned} $$
A pair is ineligible, with $y_{m,n} = f_{m,n} = 0$, for a tier mismatch, a model that does not fit into the node's memory budget, or memory pressure.
Here $\bar{\tau}(m, n)$ is the pair's average latency, with the same fallback as in Stage~1 and a nominal $\bar{\tau}_0$ for nodes without any history;
$\bar{\tau}_m$ and $\bar{\ell}_m$ are the averages of the latency and the load time over the model's eligible nodes;
and $y^0$ is the current placement, i.e.\ the last plan.

All three terms of the objective are node time per second.
The first is the inference time of the requests that replicas serve.
The second covers the requests that find no replica: each of them costs a load and an inference.
The third counts new loads, each spread over a planning horizon $T_{plan}$.
Loading a model therefore pays off roughly once one request for it is expected within $T_{plan}$.
The constraints let a node serve a model only if it holds it, keep each node within its memory budget, and keep its load below $\theta_{up}$.
When a model's demand exceeds what its nodes can serve, the program serves it partly, and the rest overflows to other nodes (Stage~1).
Loading nothing is always a valid solution, so the program is always feasible.
A tiny bonus for keeping the current placement prevents changes between equally good plans.
The program is solved with the HiGHS solver in SciPy; for the testbed, it has a few dozen variables and takes well under a second.

The program does not weigh accuracy against energy itself.
Its demand is the shadow demand of the router, which already reflects how the router trades accuracy against energy.
The program serves this demand with as little node time as possible, i.e.\ inference plus loading.
Less node time means that queries wait less, and that GPU time and memory are spent on the models in demand.
The program thus pursues the latency and resource goals, while the router pursues accuracy and energy (Section~\ref{sec:problem}).

The solution gives the target placement of each node, its models sorted by demand, and the traffic shares $w_{m,n} = f_{m,n} / \sum_{n'} f_{m,n'}$ of each model over its replicas, which the dispatch step of Stage~3 uses.
If the solver fails, the controller keeps the current placement and splits each model's traffic equally over the nodes that hold it.

\subsection{Following the Plan}

Each node reads its target placement from the shared store about once per second.
While its queue is empty, it loads one missing target model at a time.
Loading for the plan thus starts only when no query is waiting.
To make room, it may unload models outside the target, but never another target model.
A task that needs a model the node does not hold is still served: the node loads the model on demand and unloads models outside the target first, and target models only as a last resort.
Such a target model returns once the node is idle again.
Models outside the target stay loaded until their memory is needed, so the leftover memory works as a cache.
The controller renews every target placement at each evaluation, also under the fixed placement.
A target that is not renewed expires after a few seconds, and the node then falls back to the LRU cache.
A plan thus never outlives the controller that made it.
