\section{LLM Serving and Resource Management}

LLM Serving systems try to optimize the way LLM inference tasks map to specific hardware resources.
Current systems often separate and classify different tasks to further enhance this mapping.
BROS \cite{bros} distinguishes between latency-critical (RT) requests and throughput-oriented (BE) requests.
EconoServe \cite{econoserve} instead splits every request into its two phases: a prompt processing task (PT) and a token generation task (GT).
An important aspect of optimization in these systems is advanced Key-Value Cache (KVC) handling.
BROS designs a bidirectional KVC management mechanism to best fit hybrid RT and BE requests, while EconoServe maintains separate queues for PTs and GTs and designs its own KVC pipelining method.
Both papers name the KVC as a main bottleneck of LLM serving \cite{bros, econoserve}.
This explains why both systems invest so heavily in cache-level optimization.

Beyond memory, energy consumption has emerged as a critical serving constraint.
DynamoLLM \cite{dynamollm} introduces a broad energy-management framework that dynamically reconfigures the number of active instances, model parallelism, and GPU frequencies in response to fluctuating workloads.
This allows the system to minimize energy use and cost while meeting its latency targets.
As a result, it also reduces carbon emissions.
The framework decomposes its decisions into a hierarchy of controllers operating on different timescales, separating slow choices such as instance count from fast ones such as GPU frequency scaling.

Finally, systems like NexusSched \cite{nexussched} look at the layer above and try to bridge the ``information gap'' between the central cluster router and the individual inference engines.
Instead of relying on naive metrics like queue length, NexusSched uses forward-looking telemetry -- such as predicted latency and available KVC -- to make proactive routing decisions across the cluster.
The motivating insight is that these metrics lag behind the real load.
A rolling average latency describes the last few seconds, not the current state.
Also, the same queue length means very different delays on different GPU types.
NexusSched therefore replaces reactive load balancing with predictive scheduling that anticipates bottlenecks before they appear.

However, although these serving systems use the hardware efficiently -- through KVC management, request scheduling, and frequency scaling -- they look at a prompt at most to estimate its length, and they never answer an easy prompt with a smaller, cheaper model.
Disregarding this possibility means ignoring a large efficiency lever.
For example, GreenServ uses 64\% less energy than always using the largest model, while reaching a higher accuracy \cite{greenserv}.
FrugalGPT matches the best single model at up to 98\% lower cost \cite{frugalgpt}.


\section{Prompt-Aware LLM Routing}

While LLM serving asks the question ``How?'', LLM routing tries to optimize the answer to ``Who?''.
Here, the choice between models of different sizes and specializations is made.
This choice is a major factor in the trade-off between resource consumption and inference accuracy \cite{greenserv, frugalgpt, routellm}.

The most logical and the most studied approach is to make this choice by inspecting/analyzing the input prompt and route based on its features.
CARGO \cite{cargo} embeds the prompt and uses a single regression model to predict how well each LLM will answer it.
If the two best LLMs are close, both answer, and a small classifier picks the better answer.
Judge LLMs are only needed to label its training data: they compare the answers of several LLMs to the same prompts.
TagRouter \cite{tagrouter} lets a small fine-tuned LLM generate semantic tags for each prompt.
The model that has historically done best on these tags then does the inference.
Marinelli et al. \cite{noft} suggest the new metric ``Number of Thoughts'' to describe the prompt's complexity. This single value is then predicted through a random forest and used for routing.
The IRT-Router \cite{irtrouter} uses Item Response Theory. It learns the abilities of each LLM and the difficulty of each query over 25 dimensions, predicts how well each LLM will answer, and weighs this against the LLM's cost. The router is trained offline; for a new query, it only refines the query's embedding with similar known queries.

Although using the input prompt as the anchor for this choice might already seem like the best approach, there are still clear limitations to be noted \cite{lookahead}.
Lookahead \cite{lookahead} therefore also looks at the possible answers.
A small language model predicts a representation of the answer each candidate model would give, without generating the answer.
The router uses these predictions, which makes its choice better informed.
GreenServ \cite{greenserv}, the work this thesis builds on, explicitly optimizes the trade-off between accuracy and energy consumption.
To achieve this, GreenServ extracts three features from each prompt: the task type, the semantic cluster, and the text complexity.
The task type is used to express the intent (e.g.\ is this a math problem, or a summarization task?).
The semantic cluster groups the query by topic or domain.
And the text complexity describes how complex the prompt itself is.
After this, the reinforcement learning concept contextual multi-armed bandit is used to create a router that is learning continuously and online.
The features of the prompt are fed into the router, the bandit selects a model and lastly updates its preferences based on the received reward.
Although GreenServ learns online which model best balances accuracy and energy for a prompt, it assumes a single GPU server on which every model is always available.
Its latency constraint is formulated, but its released code never checks it \cite{greenserv_code}.
It is therefore the natural starting point for this thesis, and the main baseline it is evaluated against.

However, although these routers choose the best model for each prompt, they assume that model is always available: none of them checks whether the chosen model is loaded on any node and can answer in time on the current hardware state.
A decision that is right for the prompt can thus be unservable, and the resulting SLA violation is invisible to the router.
The same assumption also hides the option of serving a prompt from a nearby edge node instead.


\section{Model Placement and Autoscaling for LLM Serving}

The systems discussed so far take the set of deployed models as fixed: the routers assume that every model is available, and the serving systems change at most how many instances of a given model run, as DynamoLLM does.
A separate research area asks the orthogonal question of how the deployment itself should change over time, i.e., which models to replicate, on which devices, at what scale, in response to workload and hardware state.
Autoscalers answer this by adding or removing capacity, such as replicas, virtual machines or GPU time.
On a fixed set of nodes, the same question becomes one of placement: which models each node keeps loaded.
A recent survey of LLM inference scheduling \cite{llm_serving_survey} calls this model management: requests go to nodes that already hold their model, models are loaded before demand for them rises, and rarely used models are removed.
The survey also argues that changes to the deployment must be closely coordinated with how requests are dispatched.
In its view, future autoscalers should combine demand forecasts, dispatch logic and the choice of which models stay loaded.
This thesis works with a fixed set of nodes, so its controller decides placement.

ENOVA \cite{enova} is an autoscaler for serverless multi-GPU clusters.
It deconstructs the inference pipeline into measurable sub-stages and fits a recommendation module that maps each (LLM, GPU type) pair to an expected throughput configuration.
Furthermore, it feeds live telemetry -- request rate, pending count, GPU utilization, response time -- into an autoscaling controller that adjusts how many replicas of each model are kept.

HAS-GPU \cite{hasgpu} is much like ENOVA but at a finer allocation granularity, and it targets deep-learning inference in general rather than LLMs.
It adds vertical scaling for serverless GPU functions to the usual horizontal scaling.
Each pod gets a fixed share of the GPU's Streaming Multiprocessors (SMs) when it starts.
Vertical scaling then changes the pod's GPU time quota at runtime.
An online Kalman filter drives both kinds of scaling: it predicts the next request load from the current measurement.
Scaling decisions then reduce to two threshold tests against this prediction, and a minimum interval between scale-down operations suppresses oscillation.
Its scaling mechanisms do not carry over to higher-level inference stacks: the SM shares rely on NVIDIA's Multi-Process Service (MPS), and the time quotas rely on intercepting CUDA driver calls.
Its control loop, however, is directly relevant here.
It shows that classical state-space estimation with simple threshold rules can trigger fine-grained reallocation.

SageServe \cite{sageserve} attacks the same problem at hyperscaler scale.
Operating on production traces from Microsoft Office 365 (over ten million LLM requests per day), it co-optimizes short-term request routing with long-term GPU placement:
an ARIMA traffic forecast predicts per-region demand and an integer linear program reallocates GPU VMs and model placements every hour, subject to SLA constraints.
The authors report up to 25\% GPU-hour savings against the production baseline.
They optimize routing and placement together, instead of as separate problems.

A complementary line of work keeps the placement fixed and adapts the resources of a single device at runtime.
CLONE \cite{clone} prunes a single LLM for a single edge device, offline, and trains one LoRA adapter per task on top of it.
At runtime, a learned controller sets the voltage and frequency of the device per layer, so that the model meets a latency target with little energy, and a router mixes LoRA adapters for each prompt.
While not a cross-model placement system, it is the natural counterpart on the edge tier:
where ENOVA and SageServe ask which model lives on which GPU, CLONE asks how much capacity a fixed (model, GPU) pair can be made to yield.

However, although these systems adapt capacity to demand from live telemetry, they assume the traffic per model is given rather than chosen by a router that decides \emph{which model should answer} each query.
Their triggers also differ in how well they capture the cost of a request.
HAS-GPU's trigger looks at the request rate alone, which misses that LLM requests can differ in cost by orders of magnitude.
SageServe forecasts tokens per second, which partly captures this cost.
The common control-loop pattern they share -- ingest live telemetry, decide on a reconfiguration, dispatch -- aligns directly with the telemetry surface this thesis uses (per-node queue length, per-model latency, free GPU memory, and the loaded models with their load times and memory).
This thesis therefore integrates a placement controller of this kind on top of its routing layer: it adopts HAS-GPU's Kalman-plus-threshold trigger design -- extended with a placement rule for models without a replica and with per-(model, node) latency-deviation and memory-pressure rules, since a trigger based on request rates alone is insufficient when per-request cost, model selection, and memory pressure decouple from the arrival rate -- and a small mixed-integer program, in the spirit of the replica program of ENOVA and the placement program of SageServe, that decides from the same telemetry which models each node keeps loaded and how each model's traffic is split across them (Chapter~\ref{chapter:model}).
Unlike the systems above, the controller does not take the demand per model as given: it plans with the demand of the router, i.e.\ for every query the model the bandit would choose if every model were loaded.

\section{Research Gap and Thesis Contribution}

The three research areas leave complementary gaps:
serving systems use the hardware efficiently but never choose the model;
prompt-aware routers, GreenServ included, choose the model but not in view of the hardware state;
and autoscaling and placement systems adapt the deployment but take the traffic per model as given.
None of the surveyed systems both chooses among separate models per prompt and accounts for the live state of the nodes that would serve it, across edge and cloud.
CLONE comes closest, since it mixes LoRA adapters per prompt and meets a latency target, but it does so for one model on one device.

This thesis closes this gap by extending GreenServ's semantic bandit routing in two steps, each tied to the research questions of Chapter~\ref{chapter:introduction}.
A telemetry-driven feasibility filter restricts the bandit to models that a node can hold and is expected to serve within the latency deadline, counting the time to load a model the node does not hold.
The filter is evaluated for its effect on SLA violations (RQ1) and for what the restriction costs in accuracy and energy (RQ2).
A trigger-driven controller, combining HAS-GPU's trigger design with a placement program, decides which models each node keeps loaded, following the demand of the router;
it is evaluated against on-demand loading, an LRU cache and a fixed placement (RQ3).
