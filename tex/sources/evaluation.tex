This chapter answers the three research questions of Chapter~\ref{chapter:introduction}: whether telemetry-driven feasibility filtering reduces SLA violations (RQ1, Section~\ref{sec:eval-filter}), what restricting the choice to feasible models costs in accuracy and energy compared to GreenServ and simple baselines (RQ2, Section~\ref{sec:eval-routing}), and whether adapting each model's traffic split improves latency under shifting load (RQ3, Section~\ref{sec:eval-allocation}). Each question maps to one comparison: the full system is compared against variants with the corresponding component disabled.

\section{Experimental Setup}

\textbf{Testbed.}
% TODO: exact hardware. Placeholder description below.
The system is deployed on an edge-cloud testbed consisting of resource-constrained edge nodes and a high-capacity cloud node, connected through the shared Redis queue described in Chapter~\ref{chapter:model}. Edge nodes serve the 13 smaller models of the pool (0.5B--8B parameters), the cloud node the six larger ones (12B--34B); every node loads the requested model on demand. The scheduler runs as a gateway on the edge tier. All system parameters are set as listed in Table~\ref{tab:parameters}.

\textbf{Workload.}
Queries are drawn from the five datasets underlying the task-type feature -- MMLU \cite{mmlu} (multiple-choice knowledge questions), GSM8K \cite{gsm8k} (math word problems), HellaSwag \cite{hellaswag} (sentence completion), WinoGrande \cite{winogrande} (pronoun resolution) and CNN/DailyMail \cite{cnndm} (news summarization) --, interleaved to create a mixed stream. Each query is submitted with its dataset label and ground-truth reference, so the scheduler applies the dataset's answer extraction, quality metric and generation settings, and computes the reward online. % TODO: sample sizes, arrival process (open vs. closed loop), number of runs and seeds.

\textbf{Metrics.}
(i) SLA violation rate: fraction of queries whose end-to-end latency exceeds $T_{max}$; (ii) answer accuracy per task type; (iii) energy per query, measured at the GPU (the reward itself uses energy per token, Section~\ref{sec:problem}); (iv) the scalarised reward $r_t$; (v) for the allocation controller: trigger frequency, LP re-solve count, and time-to-recover after a load shift.

\textbf{Baselines.}
(a) \emph{Largest-model}: every query to the most capable cloud model; (b) \emph{smallest-model}: every query to the cheapest edge model; (c) \emph{random routing}; (d) \emph{GreenServ-style}: the contextual bandit without feasibility filtering or allocation control, i.e.\ the single-cloud assumption of prior routing work.
